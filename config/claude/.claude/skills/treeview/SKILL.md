# Treeview — 対象を木にして、全体の形を見る

木の価値は網羅ではなく**一望**にある。全部を写した木は原文と同じ長さになり、
俯瞰の役に立たない。ノードを 1 つ増やすたびに、読む人が一目で掴める量を 1 つ減らしている。

**出すのは木。** 表・図・改修案・長い解説は、頼まれない限り足さない。
木に添えてよいのは、**読めない語の定義**(§6)と、**木を見ても分からない観測**が数行(§7)だけ。
木の下に第二の成果物を作らない。

深さは利用者のもの。`L2` `L3` と指定されたらその通りに出す(§3)。

作る順序は、**問いを決める → A/B を判定する → 深さを決める → 木を出す → 自己点検**。

## 1. この木は何の問いに答えるか(最初に 1 行で書く)

問いが決まると、何を**描かないか**が決まる。同じ対象でも問いが違えば別の木になる。

| 対象 | 問いの例 | 木の軸 |
|---|---|---|
| チケット群 | 分割の粒度はどうなっているか | 親子 + 各枝の件数 |
| チケット群 | 今どこが詰まっているか | 親子 + 状態・進捗 |
| 文章 | 論の骨格はどう組まれているか | 主張の従属関係(見出しではない) |
| 文章 | どこに何が書いてあるか | 見出し階層そのまま |
| コード | 責務はどう分かれているか | モジュール + 依存の向き |
| コード | どこを触れば済むか | 呼び出し・依存 |

形を見るのが目的なら、**比較できる量を木に載せる**(枝ごとの件数、深さ、行数)。
量が載っていない木では偏りが見えない。

問いを書かずに木を出すと、軸が混ざる。混ざった木は**兄弟の意味が揃わない**という形で必ず壊れる。

## 2. 構造は既にあるか(A/B の判定。ここを飛ばさない)

この判定は、単に作り方を変えるだけではない。**こちらが構造の作者かどうか**を決める。
作者でないなら木は写し取ったものなので、形のずれは対象側の事実として**観測を述べるに留める**。
作者であるなら切り方に責任があるので、**なぜそう切ったかを示す**必要がある。

| | A: 抽出 | B: 分解 |
|---|---|---|
| 対象 | 親子リンク、見出し、ディレクトリ、import、設定のキー | 一続きの文章、ブレスト、口頭の計画、フラットな箇条書き |
| 木の出所 | 対象の中にある。**読み取る** | 対象の中に無い。**与える** |
| 構造の作者 | 対象を作った人 | こちら |
| 主な誤り | 出しすぎて俯瞰にならない | 無い階層をでっち上げる |
| 形について述べること | 観測のみ(§7)。良し悪しの判定や書き換え案は出さない | 観測 + **切った根拠**。自分の産物なので説明責任がある |
| 規律 | §3 | `references/decompose.md` を読んでから切る |

**混在が普通**。見出しはあるが論理が別構造の文章は、A で読み取った見出しを骨に、
B で論理の木を重ねる。そのときは「見出し階層」と「論の構造」を別の木として出す。
1 つの木に 2 つの軸を混ぜない。混在の場合、B の部分だけ B の規律に従う。

## 3. 深さ(L1/L2/L3。指定されたらその通りに出す)

深さは**利用者が決める**。指定があればそれに従い、こちらの判断で畳まない。

| 指定 | 出すもの |
|---|---|
| `L1` | 根だけ。全体が何本あるか |
| `L2` | 根 + その子 |
| `L3` | 3 段目まで |
| `L4`, `L5`, … | 同様に、その段まで |
| `全部` / `full` / 指定なしで対象が小さい | 葉まで全部 |
| 指定なしで対象が大きい | 下の既定に従い、**何を畳んだかを明示** |

**指定された深さは上限ではなく要求**。`L3` と言われたら 3 段目を全部出す。
40 行を超えても出す — 行数の既定より利用者の指定が優先される。
「L3 だと長いので L2 にしました」は指示の無視にあたる。

切った先に子があるなら、末尾に件数を出す。`… +7` は「ここから先に 7 件ある」の意味で、
深さを増やせば見えることを示す。

```
Epic #101 予約体験を作り直す                    open   1/13
├─ Story #102 予約フローを1画面に畳む            open    1/2    … +2
└─ Story #108 通知を整理する                    open    0/9    … +9
```

深さの指定が無いときの既定は、**1 画面(概ね 40 行)に収まる最大の深さ**。
L2 で収まり L3 で溢れるなら L2 で出し、「L3 以降は `… +N`。深さを指定すれば出します」と 1 行添える。
勝手に畳んだことを黙らない。

### 畳むときの規律(深さ指定が無いときだけ)

1. **同種の繰り返しは代表 + 件数**。`test_*.py ×34` は 34 行より情報が多い。
2. **葉の本文は 1 行**。既定は「名前 + 意図 1 行」。全文が要るなら木とは別に下へ並べる(木は目次として機能させる)。
3. 落としたものは必ず数で示す。木は「これで全部」と読まれるので、省略の明示が嘘を防ぐ。

### 抽出(A)のとき

**元データに無い「ノード」を足さない**。読みやすさのための中間ノードを勝手に挿すと、
それは抽出ではなく分解になる。括りたくなったら、それは B の仕事だと判定し直す。

**数えた結果は足してよい。** 件数・深さ・状態の集計は元データから導けるもので、
解釈が入らない。むしろ偏りを見るには要る(§1)。足してはいけないのは、
こちらの判断が入るもの — 新しい親、分類、並べ替え、優先度。

### 読み取り元が API のとき

チケット階層のように取得に API が要る対象は、木を描く前に**取り方**を確かめる。
GitHub Issues の親子・進捗の取得コマンドは github-tickets の `references/gh-commands.md` にある。
自分で組み立てず、そこを読む。木の形は §5 の記法に揃える。

## 4. B(分解)— `references/decompose.md` を読む

無い階層を与えるので、切る基準・自己検査・根拠の示し方が要る。分量があるので別ファイルにした。
**B と判定したら、切り始める前に `references/decompose.md` を読む**。
記憶で切らない — 4 つの検査と、文章を論理で切る手順がそこにある。

## 5. 記法(揃える。ここを毎回作り直さない)

```
Epic #101 予約体験を作り直す                    open   3/12
├─ Story #102 予約フローを1画面に畳む            open    1/2
│  ├─ Task #103 日付ピッカーを差し替える          done
│  │   既存カレンダーが 375px 幅で崩れるため
│  └─ Task #104 確認画面を廃止する               open
└─ Story #105 キャンセルを利用者に開放する        open    0/2
   … +2 (Task, 全て open)
```

- 罫線は `├─ └─ │`。等幅前提。装飾記号や絵文字は使わない(目が滑る)。
- 1 ノード 1 行。意図を添えるときは次行にインデントして 1 行だけ。
- 状態・進捗などの属性は**右に寄せて列**にする。行中に混ぜない。
- **数の列は、何を数えたかを 1 行で書く**(「右の列は直下の子の数」「closed/全子孫」)。
  書かないと、読む人は別の数え方だと思って読む。同じ木の中で数え方を変えない。
  観測で数に触れるときも同じ数え方にする — 木に `1/16`(全子孫)と出して観測で「13 件」(Task のみ)と
  書くと、どちらかが誤りに見える。単位を変えるなら、変えたことを書く。
- 省略は `… +N` と、何を落としたかを括弧で。
- 番号や ID があるなら必ず出す。俯瞰の次の行動は「その 1 件を開く」なので、
  開くための鍵が無い木は片手落ち。

出力先はターミナルの整形テキストが既定。盤面が大きく折りたたみやリンクが要るときだけ
Artifact(HTML)にする。その場合も木の形と記法はここに揃える。

## 6. 用語を定義する(木だけでは読めない語があるとき)

木は 1 ノード 1 行なので、**語がそのまま意味を運ぶ**。読む人がその語を知らなければ、
木の形が見えていても中身が分からない。そこで、木の下に用語の定義を置く。

定義するのは、次のどれかに当たる語。

| 当たる語 | 例 |
|---|---|
| その対象の**固有語**(組織・製品・コードベースの内部用語) | `F2`, `formation`, `指揮層`, `souzai` |
| 一般語だが、**ここでは特別な意味**で使われている | 「観測」「枠」「寄せる」 |
| **略語・記号**で、展開しないと読めない | `CS`, `L4`, `PVT_`, `#101` |
| 木の**階層名そのもの**が自明でない | `Epic` / `Story` / `Task` が何を指すか |

判定は 1 つ。**辞書を引いて分かる語は定義しない。** 引いても分からない語だけ定義する。
「計測」「レビュー」「実装」は引けば分かるので載せない。`F2` `道具の品格` は引いても出ないので載せる。

**語の一覧が木より長くなったら、載せすぎ。** 主役は木で、語は木を読むための補助。
木が 30 行なら語は多くて 10 行程度に収まるはず。超えたら、辞書で引ける語が混ざっている。

書き方は、木の直後に `語 — 定義` を 1 行ずつ。定義は名詞句で短く。

```
語:
  F2 — 量産プロセスの第 2 段階。仮説カードが実装に入る前の収束ループ。
  スピン — 仮説カードを 1 周回して精度を上げる反復。
  道具の品格 — 量産アプリが「AI が作った物」に見えないためのデザイン規範。
```

木の中で使った記号(`… +N`、`再掲`、`循環`、`葉`)も、初めて出すなら 1 行で説明する。
これらは木の読み方そのものなので、抜けると木が読めない。

出典があるなら添える。定義の根拠が対象の中にあるなら行や節を指し、
外の規約なら**その規約のあるファイル**を指す(`Epic/Story/Task の定義: structuring-work`)。
出典の無い定義は、こちらの解釈なのでその旨が分かるように書く。

## 7. 形の観測(**木を見れば分かることは書かない**)

主役は木。観測は木の補助であって、第二の成果物ではない。
**木を見れば一目で分かることを、下に文章で書き直さない** — 枝の偏りは木に件数が載っていれば見える。
書くのは、**木の上では見えにくいこと**だけ。多くて 3 行、無ければ 0 行でよい。

| 書く(木では見えにくい) | 書かない(木を見れば分かる) |
|---|---|
| 離れた枝にある同じ題名(並べて比べないと気づかない) | 「#108 の下に 9 件」(木に `0/9` と出ている) |
| 同列ノードの抽象度のずれ(語の質の違いで、形には出ない) | 「#118 は 1 子」(木を見れば分かる) |
| 全体の集計(全 22 件中 closed 1 件) | 「3 つの Epic がある」 |

見るのは個々のノードの中身ではなく、**枝の格好**。

| 形 | 観測されること |
|---|---|
| 枝の大きさが極端に偏る | 1 つの枝に構造が集中している(件数を添える) |
| 1 本だけ深い | そこだけ深さが違う |
| 全体が平ら(深さ 2 で幅が広い) | 中間の階層が無い |
| 同じ語・同じ題名が離れた枝に出る | 同じものが 2 か所にある |
| 子が 1 つの親が続く | その段が分岐していない |
| **同列のノードで抽象度が違う** | 兄弟が同じ軸で切られていない(例: 「通知を整理する」と「予約フローを1画面に畳む」が同列) |
| 葉ばかりで中間が薄い | 親が名前だけで、内容を持っていない |
| 空に近い枝がある | 子を持たない枝がある |

**観測に留める。** 述べるのは「そうなっている」までで、「だから良い/悪い」「こう直すべき」は
書かない。読む人はたいてい対象の事情を知っており、偏りが意図的かどうかを判断できるのは
その人。こちらが判定すると、見るための道具が勝手な批評に変わる。

書き方は「どこが・どうなっているか」を 1 行。数を添えると読む人が自分で判断できる。

```
形:
- #112「メールテンプレートを共通化する」と #122 が同じ題名で、別の Epic の下にある。
- #108「通知を整理する」は、同列の #102「予約フローを1画面に畳む」より粒度が粗い。
- 全 22 件中 closed は 1 件。
```

例外は B(分解)のとき。自分が切ったのだから、**なぜそう切ったか**は述べる
(`references/decompose.md`)。ただし他人の構造について良し悪しを言わない点は同じ。

木を見せる場では構成を**変えない**。並べ替えも統合も、利用者の指示を経てから。

### 木が元データを写しきれないとき

対象に循環や複数の親があると、木にした時点で辺が落ちる。**木は出す**が、
落ちた分を 1 行だけ添える(`core/models.py は 7 箇所から参照されており、木では 1 箇所にのみ表示`)。
黙って落とすと、木が嘘をつく。辺を 1 本も落とさず見たい場合は diagramming。

## 自己点検(出す前に必ず)

- **深さの指定(L1/L2/L3 等)に従ったか。**指定より浅く畳んでいないか
- 問いを 1 行で書いたか。木はその問いに答えているか
- A/B を判定したか。B なら `references/decompose.md` を読んだか
- A なのに、元データに無い中間ノードを足していないか
- 省略を `… +N` で明示したか。黙って落としていないか
- ID/番号など、次に開くための鍵が入っているか
- 読めない語を定義したか(§6)。逆に、**辞書で引ける語**を定義していないか
- 語の一覧が木より長くなっていないか。なっていれば載せすぎ
- 数の列は、何を数えたかを書いたか。木と観測で数え方が食い違っていないか
- 観測が**木を見れば分かること**の書き直しになっていないか。なっていれば消す
- **A なのに良し悪しや修正案を書いていないか**
- 木以外のものを足していないか(表・図・改修案は、頼まれない限り出さない)

## Red Flags

- 深さを指定されたのに「長いので」畳んだ
- 問いを書かずに木を出した
- 原文とほぼ同じ長さの木になった(転記であって俯瞰ではない)
- 属性が行中に散っていて、列として読めない
- 循環や多重の親があるのに、落ちた辺を黙っている
- 「文章構造」と言われて、論理ではなく見出しだけを写した
- 木を見れば分かることを、下に文章でもう一度書いた
- 頼まれていない表・図・改修提案を足した
- 深さの指定が無いのに 40 行を超え、畳んだ旨も書かなかった
- 観測が木の**中身**の話になっている(「#14 は重要」等)。観測は**形**の話
- 読む人が知らない固有語・略語を、定義せずに木に並べた
- 逆に、辞書で引ける語まで定義し、語の一覧が木より長くなった
- 木の数の列と観測の数が食い違っている(数え方を変えたのに書いていない)
- A なのに「#108 は分割すべき」「統合したほうがよい」と評価した
- 観測を出すついでに、断りなく構成を書き換えた
- B なのに `references/decompose.md` を読まず、記憶で切った

## 受け渡し

- 分解の規律(B) → `references/decompose.md`
- 起票のための分解 → **structuring-work**(Epic/Story/Task の階層規則と検査表はそちら)
- 辺を落とさず見たい / 循環を図にしたい → **diagramming**
- チケット階層の取得コマンド → **github-tickets** の `references/gh-commands.md`
- セッション/エージェントの木 → **session-map**(専用の木があるので、こちらで作り直さない)
