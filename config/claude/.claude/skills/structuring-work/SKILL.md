# Structuring Work — チケットにする前に、規則で切る

登録の前に構造を決める。出力は固定形(検査表 → 木 → 保留)で、登録スキル
(github-tickets 等)はそれを受け取るだけ。トラッカーは問わない。

**原則**: チケットは「登録した」ことに価値はなく、「後から読んだ人が動ける」ことに
価値がある。ノードを 1 つ増やすたびに、読む人の時間を 1 つ減らしている。

## 階層(何に答えるかで決まる。大きさではない)

| 階層 | 答える問い | 完了の観測 | 観測可能な条件 |
|---|---|---|---|
| Epic | なぜここに投資するのか | 製品か数字に成果が現れる | 新設は利用者の確認を経てのみ。ただし**文脈を失う木**(下の「投資の問い」)を検出したら、Epic 候補と投資理由の草案を出して確認を求める。勝手に立てない・黙って省かない、の両方。既存の Epic があればその下に付ける。「別リポジトリが使える」「再現可能になる」は成果の観測ではない |
| Story | 利用者(または呼び手)が新たに何をできるか | 誰かが端から端まで実演できる | **今の範囲で、このリポジトリで**実演できる。実演の主語や置き場が別リポジトリなら、ここでは Story にせず保留に「相手側で起票」と書く。Story の下に Task が 1 つも要らないなら、それは Task |
| Task | どの具体的変更がそれを可能にするか | 変更がマージされる/物が存在する | **完了条件を今書ける**(マージ可能な変更、または存在する物)。書けなければチケットではない。完了が**同じ 1 つの PR**で観測される変更は 1 Task(穴 8 件を 1 回の仕様改訂で直すなら Task 1 つ)。題名に具体を書けない仮置き((穴4)等)は作らない |

Story の判定が要。「DB に列を足す」は Story ではない(誰も何もできない)。
「利用者が自分の予約を取り消せる」は Story。層(DB / API / UI)で切った物は
Story ではなく、縦に切り直す(references/splitting.md)。

## 投資の問い(木を出す前に 1 回)

Story と Task だけの木は、単独で置かれると「なぜやるか」を失う。次の**どれか 1 つ**が
観測されたら、その木は文脈を失う:

- Story が 2 本以上あり、共通の目的がどのノードの題名にも書かれていない
- Story の意図に「次の〜が通る」「〜できるようにする」のような**手段**しか無く、それで
  誰の何が変わるかが書かれていない
- 入力が計画書・方針文書・PoC・投資判断・可能性探索から来ている(目的はそこに書いてあり、
  チケットには写っていない)

観測されたら、木の前に **Epic 候補**を出す: 題名(動詞の成果)+ 解決する課題 / 成功指標 /
スコープ外 の 3 項の草案。利用者がそれを認めるか直すまで起票しない。観測されなければ
Epic 候補は出さず、Story と Task だけでよい(単発のバグ 1 件に Epic は要らない)。

## 検査表(全ノード必須。表を出さずに木を出さない)

各候補ノードに対して 1 行。判定は ✓ か ✗ だけ(△ や「条件つき ✓」は ✗)。✗ が 1 つでもあれば、そのノードは**移動・統合・保留**の
どれかにし、そのまま登録しない。他トラッカーから来た項目の旧レベルは証拠にならない。

| 検査 | 判定 | ✗ のときの処置 |
|---|---|---|
| 題名が動詞の成果で終わり、80 件の一覧で単独で読める | | 書き直す |
| **他者の**承認・合意・レビューを待つ行為ではない(成果物が残らない) | | チケットにしない。PR レビューかコメントで行う。評価表・判定記録など**物が残る**作業は Task |
| 前提が**木の外**にない(たまるべきデータ、別リポジトリの裁定、未検証の実現性)。木の中の別ノードへの依存は順序であって前提ではない | | 保留に置き、**着手できる観測条件**を 1 行書く |
| 手順の一段(一覧化する、案を書く、確定する)ではなく、成果 | | 手順を畳んで成果 1 つの Task にする |
| 完了条件を今、検証可能に書ける | | 保留 |
| 上の階層表の条件を満たす | | 階層を下げる(Epic→Story→Task)か、Epic を外す |
| 既存の Epic / Story と重複しない | | 既存に付け替える |

**出力の形(この順で、全部)**:
0. 投資の問い(観測された条件と Epic 候補の草案。観測されなければ「該当なし」と 1 行)
1. 検査表(1 ノード 1 行、✓/✗、✗ の処置)
2. 木(`Epic:` / `├─ Story:` / `Task:`、各ノード 1 行の意図)
3. 保留(チケットにしない物と、その理由または着手条件)

これを登録スキルに渡す。登録スキルは階層を変えない。

## 分割(1 ノードが大きすぎるとき)

まず SPIDR(Spike / Paths / Interfaces / Data / Rules)の 5 軸で切れるか見る。
切れなければ Lawrence の 9 パターン。表と判定条件は references/splitting.md。
縦に切る(1 切片が単独で実演できる)。横(層)に切った物は分割ではなく分業。

## 合理化(基準線で実際に出た言い分)

| 言い分 | 実際 |
|---|---|
| 「前提条件を Task にしておけば着手可否が一目で分かる」 | 完了条件が書けない Task は消化できず、ボードに残る。保留に条件つきで置けば同じ可視性が出る |
| 「承認をチケットにしないと追跡できない」 | 承認は PR に紐づく。チケットにすると「誰かが作業する物」に見え、担当が宙に浮く |
| 「手順を Task に分ければ進捗が見える」 | 見えるのは手順の消化で、成果ではない。手順は実装者が変えてよい物 |
| 「残件 1 件ごとに Epic を立てれば整理される」 | Story 1 本の Epic はフォルダ。階層が意味を運んでいない |
| 「アイデアも Task にしておけば忘れない」 | 忘れないための場所は保留。Task にすると未着手のまま腐り、本物の Task を埋める |
| 「利用者が Epic を名指ししていないから Story と Task だけでよい」 | 名指しが無いのは、聞かれていないだけのことが多い。文脈を失う条件に当たれば Epic 候補を出して聞く |
| 「別リポジトリが使うのだから成果はリポジトリの外」 | 外にあるのは利用者の体験。別リポの開発者が呼べることは成果ではない。Epic の新設条件は (a)(b) の 2 つだけ |
| 「穴ごとに Task にすれば追跡できる」 | 追跡されるのは 1 つの PR。同じ PR で閉じる物を割ると、消化のためだけの close が増える |
| 「前提はあるが作業自体は進められるので △」 | △ は無い。前提が 1 つでもあれば保留に条件つきで置く |
| 「木を先に出して、細かい検査は登録時に」 | 登録は取り消せない(close しても残る)。検査は木の前 |

## Red Flags

- 検査表なしで木を出している
- Epic の下に Story が 1 本
- 題名が「〜の承認を得る」「〜の合意を取る」(他者の行為を待つ物)
- Task の題名が「〜を一覧化する」「〜案を書く」「〜を確定する」の三連
- ノード数が入力の項目数の 3 倍を超えた
- 「保留」が空(たいてい、保留すべき物を Task にしている)
- 利用者が名指ししていない Epic を「まとまりが良いから」立てている
- 投資の問いを「該当なし」で済ませたのに、Story が 2 本以上ある
- 検査表に △ がある

## 受け渡し

- 登録: **REQUIRED NEXT:** github-tickets(manifest にそのまま写る形で木を渡す)
- 本文の書き方(意味で書く、手順を書かない): backlog-create の規律と同じ
- 木が要らない単発(バグ 1 件、タイポ)は検査表 1 行だけで Task にする。Epic を立てない
