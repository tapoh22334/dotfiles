# Backlog Suspend — 状態を保存して離れる

離席の合図が出た。だが今、手元には未コミットの変更、途中のデバッグ、溜まった
レビューがある。このまま閉じると、次に開いたとき「どこまでやったか」を
スクロールバックから掘り起こす羽目になる。

このスキルの仕事は、**プロセスをサスペンドするように**セッションを畳むこと。
ただ止めるのではない。実行状態をディスクに書き出してから止める OS の
suspend と同じで、鍵の場所を残してから離れる。対になる `backlog-resume`
は、ここで残した記録から作業を再開する — だからこのスキルの成果物は、
resume が読める形で残っていなければならない。

## なぜ「記録するだけ」では足りないか

`summarize` は画面に要約を出すが、記録は残さない(揮発する)。次の
セッションはそれを読めない。このスキルは**世界を変えてから離れる** —
作業を安全な地点まで運び、再開に必要な文脈を Backlog.md に**書き込む**。
戻ってきたときに読むのは記憶ではなく、残した記録になる。

## 三段の儀式

離脱は順番に三つ。飛ばさない。

### 1. キリのいい状態を作る(安全な操作は自動、破壊的は確認)

中途半端な作業ツリーは、それ自体が「次回の負債」になる。だから記録の前に、
まず**再開しやすい地点まで作業を運ぶ**。

- **未コミットの変更**があれば、内容を確認し、意味のある単位でコミットする。
  デフォルトブランチ上なら先にブランチを切る(そのままコミットしない)。
  ブランチは**一本にまとめる** — 作業に対応するブランチが既にあればそこに
  積み、`wip/` と `review/` のような重複ブランチを増やさない(散らかりは
  それ自体が次回の負債)。
- **コミット済みで未 push** のブランチは push する。
- レビュー/引き継ぎに値する差分なら **draft PR** まで出しておく。次に開く
  人(未来の自分)が URL 一つで差分を見られる状態にする。

これらは安全(取り消せる・前進のみ)なので確認せず進める。一方で
**取り消せない操作は必ず確認**する — main への merge、force push、削除、
外部への公開/送信。ここで止まって聞くのは正しい停止であって、儀式の放棄
ではない。

判断に迷ったら基準は一つ:**「明日の自分がこの git 状態を見て、5 秒で
状況を思い出せるか」**。思い出せない散らかりは畳む。

### 2. 価値ある文脈だけ Backlog に記録する

ここが再開コストを決める。ただし**全部を記録するのは逆効果** — どうでも
いい状態まで管理すると、管理コストが再現コストを上回る。

原則:**再現困難なものだけ残し、容易に再現できるものは捨てる。**

- **残す価値があるもの**(頭の中にしかなく、失うと痛い):
  - レビューの現在地:何をレビュー中で、どこまで見て何を OK と判断し、
    どこに懸念が残っているか(単なる「◯行目まで」ではなく)
  - デバッグの現在地:立てた仮説/潰した仮説と**その根拠**/次に疑う場所
  - なぜこの方針にしたか(コミットの diff からは読めない判断の理由)
  - 次にやると決めていた一手と、その狙い
- **捨てていいもの**(いつでも作り直せる):
  - コードを読めば分かる構造、git log でたどれる履歴
  - 「テストを流す」等、コマンド一つで再現できる手順
  - 一般論・当たり前の次ステップ

記録先は Backlog.md タスク。まず `backlog task list --plain` で今の作業に
対応するタスクを探す。あれば `--append-notes` で再開文脈を足し、離脱を示す
状態(通常は `In Progress` のまま、または合意済みなら `To Do` へ戻す)に
する。**対応するタスクが無く、かつ残す価値のある保留がある場合のみ**新規
タスクを作る(`backlog task create`)。この環境の運用は下の「Backlog 連携」
を読む。

#### 位置ではなく意味を書く(最重要)

記録は未来の自分への申し送りだ。ここで一番やりがちな失敗は、**位置情報
だけ書いて意味を落とす**こと。「navigator-list.sh の 588 行目まで確認」
「line3-new まで見た」——これは行番号でしかない。明日読んでも「で、何の
話だっけ」となる。差分やコード自体は git にある。記録に残すべきは、
**コードを見ても復元できない頭の中身** — 何を・なぜ・次にどう判断するか。

各項目に、位置ではなく意味を持たせる:

- **何をしていたか(主題)**: 「Queue view の PR レビュー」。単に
  「navigator-list.sh」ではなく、それが何の作業の一部なのか。
- **どこまで進み、その判断は何だったか**: 「`_compose_row` の幅計算は
  問題なしと確認」。「◯行目まで」ではなく「◯を見て、こう判断した」。
- **何が引っかかっているか(なぜ止まったか・気になった点)**: 「
  `switch_to_queue` が外部セッションに attach しないか要確認 —
  今回の変更の要注意点」。
- **次の一手と、その狙い**: 「その関数を読んで attach 先を確かめる。
  tile/tail と同じハンドオフになっているのが期待」。

**悪い例(位置だけ)**:
> navigator-list.sh を line3-new まで確認。残り: 残部レビュー未完了。

**良い例(意味入り)**:
> Queue view の PR レビュー中。`_compose_row`(右カラム整列)まで見て
> 幅計算は OK と判断。残る懸念は `switch_to_queue` のハンドオフ —
> 外部セッションに attach しようとしないかが今回の要注意点。次は
> その関数を読んで、tile/tail と同じ挙動か確かめる。

同じ長さでも、後者は戻った瞬間に文脈が立ち上がる。抽象的な「レビュー
継続」でも、機械的な「◯行目」でもなく、**その中間の「意味のある現在地」**
を書く。

### 3. 閉じられる状態を報告する

儀式が済んだら、ユーザーに**今どうなっているか**を短く報告する:

- 何をキリのいい地点まで運んだか(push した URL、開いた PR)
- どのタスクに何を記録したか(TASK-ID と一行要旨)
- あえて捨てたもの(「デバッグ用の print は再現容易なので破棄した」等)
- 次に開いたとき最初に見るべき場所

これで安全に離脱できる。報告は「儀式の完了証明」であって、途中経過の物語
ではない。

## Backlog 連携(この環境)

このプロジェクトは Backlog.md(`backlog` CLI)でタスクを管理している。
儀式の前に一度 `backlog instructions overview` を読み、記録の直前に
`backlog instructions task-execution`(notes/plan/status の正しい足し方)を
読む。task md を直接編集せず、必ず `backlog` CLI 経由で書く — メタデータと
履歴の一貫性が壊れるため。

Backlog が無いプロジェクトでは、記録先を切り替える:リポジトリに `TODO` の
慣習(既存の TODO.md、ドキュメント、issue)があればそこへ、無ければ
**キリのいい状態を作ること自体を厚めに**やり(コミットメッセージと PR
本文に再開文脈を書き込む)、Backlog への記録は省く。記録媒体が無いのに
新しいファイルを作らない — 散らかりを増やすだけになる。

## やってはいけないこと

- **投げ捨て**:記録せず、あるいはキリの悪い状態のまま閉じる。次回の負債。
- **過剰記録**:再現容易なものまで書く。管理コストが再現コストを超える。
- **抽象的な申し送り**:「続きをやる」しか書かない。再開地点が特定できない。
- **位置だけの申し送り**:「◯行目まで」「◯ファイルを確認」で終わる。
  行番号は git にある。意味(何を・なぜ・次の判断)が抜けると読めない。
- **確認なしの破壊的操作**:main への merge、force push、削除を勝手にやる。
- **記録媒体が無いのにファイルを新規作成**:散らかりを増やす。
