# Thinking Moves

思考の詰まりには型がある。型が違えば効く手が違う。このスキルは
**症状を読んで手を選び、実際に回す**ためのものであって、技法の一覧ではない。

技法の詳細な手順・起源・エビデンスは `references/frameworks.md` にある。
選んだ後で必要な分だけ読む。最初から全部読む必要はない。

## なぜ選択が本体なのか

技法を20個並べても役に立たない。実務で失敗するのは「知らないから」ではなく
**「詰まっている種類を取り違えて、効かない手を打つから」**である。

案が出ない状態で評価基準を精緻化しても案は増えない。
案が多すぎる状態でさらに発散しても決まらない。
問いが歪んでいる状態でいくら案を出しても、全部が的外れになる。

だから最初にやることは、技法を思い出すことではなく**詰まり方の診断**である。

## 手順

### 1. 症状を判定する

ユーザーの言葉と、会話の状態から、いま何が起きているかを見る。
自己申告をそのまま受け取らないこと。「アイデアが欲しい」と言われても、
実際には問いが歪んでいるだけで、発散しても徒労に終わる場合がある。

| 症状 | 打つ手 | 詳細 |
|---|---|---|
| 案が少ない・出てこない | ブレインライティング / Crazy 8s / SCAMPER(既存物の改良なら) / 形態分析 | §発散 |
| 案は多いが選べない | KJ法でグルーピング → ドット投票 or インパクト×労力 or NUF | §収束 |
| 同じ案ばかり出る | ランダム入力 / プロヴォケーション / TRIZ矛盾 / 類推・生物模倣 | §袋小路 |
| 問いそのものが歪んでいる | 抽象化のはしご / How Might We / JTBD | §再定義 |
| 全員がすぐ同意する | 本物の反対者を立てる / プレモータム / 黒帽子 | §批判 |
| 良さそうだが不安 | **プレモータム**(最優先) / 反証条件の事前明示 | §批判 |
| AをよくするとBが悪化する | TRIZの矛盾定式化 / 反転 | §袋小路 |
| 原因が一つに絞れず再発する | 因果ループ図 / レバレッジポイント | §構造分析 |
| 抜け漏れが怖い(分析局面) | MECE / ロジックツリー | §構造分析 |
| 調べる時間がない | 仮説思考(+反証志向とセット) | §構造分析 |
| どの手を使えばいいか分からない | Cynefin で領域判定してから選び直す | §メタ |
| 発散と収束が混ざって空中分解 | Double Diamond でフェーズを分ける | §メタ |

判定がつかないときは Cynefin(`references/frameworks.md` §5.4)で
問題の領域から入る。領域が変われば正当な技法が変わる。
複雑系(Complex)の問題に「ベストプラクティス」を当てるのは誤りで、
小さく安全な実験から始めるのが筋になる。

### 2. 選んだ手を名指しして、理由を1行で言う

黙って実行しない。「いま案が3つしかないので、まず発散します。既存物の
改良なので SCAMPER を使います」のように、**診断と選択を可視化する**。

書くのは**技法の名前と理由**であって、このスキルの名前ではない。
「thinking-moves スキルの手順に従い」のような内部実装への言及は、
ユーザーにとって意味がないので書かない。SCAMPER や KJ法 は
一般に通用する技法名なので出してよい。

理由は、ユーザーが診断の誤りに気づけるようにするためである。
「いや、案の数は足りていて、決められないのが問題」と訂正が入れば、
そこで手を変えられる。黙って走ると、間違った方向に大量に出力してしまう。

### 3. 実際に回す

説明で終わらせない。技法を使って**結果を出す**のがこのスキルの仕事である。
「SCAMPER という手法があります」は失敗。「SCAMPER の7観点で案を出しました」が成功。

### 4. 発散したら必ず収束させる

発散は途中経過であって成果物ではない。30案を並べて終わるのは、
ユーザーに選択の負荷を丸投げしている。**必ず絞り込みまでやる**。

ただし絞り込みの基準は明示する。何を重視して落としたかが見えないと、
ユーザーは判断を検証できない。

## 発散 — 案を増やす

**声出しブレストの模倣をしない。** 集団ブレストが個人の総和に劣ることは
繰り返し実証されている(Diehl & Stroebe 1987 ほか)。原因は production blocking
(他人が話している間は考えられない)と evaluation apprehension(評価が怖くて
奇抜な案を出さない)である。

**これは Claude にとって有利な事実である。** エージェントを並列に
fan-out すれば、互いを見ずに独立に発想し、後で統合できる。これは
人間の集団では実現しにくい nominal group そのものになる。

**ただし fan-out は既定の手段ではない。** 起動と待機のコストが大きく、
多くの場面では自分で複数の軸を立てて発想するほうが速く安い。
fan-out を使うのは次の条件が揃ったときに限る:

- 20案以上が本当に必要
- 軸が3つ以上あり、軸ごとに独立に考えさせる意味がある
- ユーザーが待てる場面である(即答が要る相談では使わない)

条件を満たさないなら単独で回す。相談に対してエージェントを4体起動して
待たせるのは、技法としては正しくても実務としては失敗である。

主な手:

- **ブレインライティング(6-3-5)** — 3案書く → 他者の案を見て発展させる → 繰り返す。
  エージェント fan-out で再現するなら、第1ラウンドは互いを見せず、
  第2ラウンド以降で他者の案を入力に渡す。
- **SCAMPER** — 既存物があるときに強い。代用/結合/応用/修正/転用/削除/逆転の7観点。
  白紙から考えるより効率がよい。
- **形態分析** — 軸を立てて組み合わせを機械的に列挙する。網羅性が要るとき。
  組み合わせ数が爆発するので、実行可能な組だけ残す剪定が要る。
- **Crazy 8s** — 短時間で数を強制する。質より量のフェーズに限る。

量の目安は問題による。ただし**「3案出して終わり」は発散していない**。
最初に出る3案は、たいてい既に誰かが考えたものである。

## 収束 — 絞り込む

発散の直後は案が雑多に散らばっている。いきなり投票すると、
似た案が票を分け合って、実際には強い方向性が死ぬ。

だから**まずグルーピングしてから選ぶ**:

1. **KJ法** — あらかじめカテゴリを決めずに、似たものを寄せてから
   後で名前をつける。先にカテゴリを決めると既存の枠に押し込むだけになる。
2. 各グループの代表案を立てる
3. 基準で絞る:
   - **インパクト×労力** — 2軸のマトリクスに置く。直感的で速い
   - **NUF**(New / Useful / Feasible) — 3観点を各10点で採点。定量的に比較したいとき
   - **ドット投票** — 人間が複数いるとき。Claude 単独では意味が薄い

絞った後、**落とした案の中で惜しいものを1つ挙げる**とよい。
なぜ落ちたかが見えると、ユーザーは基準そのものを検証できる。

## 袋小路 — 同じ案ばかり出るとき

発想が同じ場所を回っているときに、さらに発散しても同じ案が出る。
**パターンそのものを壊す**手が要る。

- **ランダム入力** — 無関係な語を強制的に持ち込み、接続を探す。
  「このゲームと『洗濯機』を結びつけると?」のような問い。
  馬鹿げて見えるが、既存の連想経路を外すのが目的である。
- **TRIZの矛盾定式化** — 「AをよくするとBが悪化する」を明示的に書く。
  矛盾を言語化すること自体が仕事の半分で、書いた時点で
  「そもそも両立不可能という前提が本当か」を問える。
- **反転** — 「どうすれば確実に失敗するか」を考える。
  Munger 流。正面から考えて出ないものが、裏から見ると出る。
- **類推・生物模倣** — 別の領域で同じ構造問題がどう解かれているかを探す。

## 再定義 — 問いが歪んでいるとき

**案が出ないのではなく、問いが間違っているケースは多い。**
ここを見落とすと、正しく解いた結果が的外れになる。

- **抽象化のはしご** — 「なぜそれが要るのか」で上に登り、
  「具体的にはどうやるか」で下に降りる。登ると問いが広がり、
  降りると実行可能になる。詰まったら一段上に登ってみる。
- **How Might We** — 問題文を「どうすれば〜できるか」の形に言い換える。
  広すぎると発散しすぎ、狭すぎると解が1つに固定される。粒度の調整が肝。
- **JTBD** — 「ユーザーは何を雇っているのか」。機能ではなく
  片付けたい用事で捉え直す。

## 批判 — 出したものを壊しにいく

ここは**プレモータムを最優先**にしてよい。この文書が扱う技法の中で、
実証的裏付けが最も厚いものの一つである(prospective hindsight により
検出されるリスクが増えるという実験的検証がある)。

**プレモータムの手順:**

1. 「このプロジェクトは**失敗した**」と完了形で宣言する。仮定ではなく既成事実として置く
2. その状態から逆算して「なぜ失敗したか」の理由を列挙する
3. 出た理由のうち、いま手を打てるものを対策する

「失敗するかもしれない」ではなく「失敗した」と断定するのが要点である。
可能性を問うと人は防衛的になるが、既成事実として原因を問われると
具体的な穴が出てくる。

**役割としての悪魔の代弁者には注意する。** 「君は反対役ね」と割り当てると、
かえって多数派が自説を補強する(cognitive bolstering)ことが示されている
(Nemeth 2001)。**本物の反対意見**、つまり実際にそう考えている視点を
探すほうが効く。Claude が批判役を演じるときは、演技ではなく
本当に弱点だと思う箇所を突くこと。

**反証条件の事前明示** — 「これが間違っているとしたら、何が観測されるはずか」
を先に書く。後から言い訳を作れなくするための装置である。

## 構造分析 — 発想ではなく分析が要るとき

問題が「思いつかない」ではなく「見通せない」ときは、発想技法は効かない。

- **MECE / ロジックツリー** — 漏れなく重複なく分解する。
  完全な MECE には到達しないという前提で運用する。
- **仮説思考** — 先に仮説を立て、それを検証する順に調べる。
  時間が限られるとき。**確証バイアスに注意**し、反証志向とセットで使う。
- **システム思考** — 対策しても別の場所で再発するなら、フィードバックループを疑う。
  因果ループ図を描き、レバレッジポイントを探す。パラメータをいじるより
  ゴールやパラダイムのほうが効くというのが Meadows の主張である。

## メタ — どの手を使うか分からないとき

**Cynefin** で問題の領域を判定してから選び直す。領域が違えば正当な手が違う。

| 領域 | 性質 | 取るべき行動 |
|---|---|---|
| Clear | 因果が明白 | ベストプラクティスを踏襲 |
| Complicated | 専門知識で解ける | 分析・専門家 |
| Complex | やってみないと分からない | 小さく安全な実験(Probe-Sense-Respond) |
| Chaotic | 混乱している | まず行動して止血 |

複雑系に「正解の手順」を求めるのは誤りである。実験して学ぶしかない。

**Double Diamond** は工程の設計に使う。発散と収束が同じ場で混ざると
両方が機能不全になるので、フェーズとして分ける。

## 誠実さについて

技法によってエビデンスの厚みは大きく違う。**「効くと証明されている」と
過大に語らない。**

- **実証が厚い**: プレモータム、声出しブレストの非効率性、本物の反対 vs 役割の反対
- **理論は強いが効果測定は限定的**: TRIZ、Cynefin、システム思考
- **逸話が中心**: 水平思考、Six Hats、反転、JTBDのミルクシェイク

使う価値がないという意味ではない。ただし「有名だから効く」ではないことは
意識しておく。**最も広く使われている古典的ブレストが、最も明確に
効果を疑問視されている**という逆説がある。

## 他スキルとの境界

- 失敗の原因究明 → `five-whys-root-fix`
- やり方そのものへの批判 → `metalize`
- 既存物の調査(車輪の再発明回避) → `prior-art-survey`
- 主張の真偽の査読 → `adversarial-review`

このスキルが担うのは**生成と決定**である。まだ無いものを作り、
複数あるものから選ぶ局面で使う。
