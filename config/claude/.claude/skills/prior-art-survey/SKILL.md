# Prior Art Survey — 着手前の棚卸しと地ならし

## なぜこれが要るのか

コードを書き始めた瞬間、判断は「どう作るか」に固定される。「そもそも作るのか」を
問い直す枠は、着手後には二度と開かない — 書いたものが埋没費用になり、既存物は
「今さら乗り換えるコスト」として評価されるようになるからだ。だから調査は着手の
**前**に、独立した工程として置く。

そして調査には**二つの半分**があり、片方だけでは足りない:

- **先行実装(供給側)**: 同じものが既にあるか。使えるか、改造できるか
- **体系知識(規範側)**: この領域で人類が既に分かっていること。定石・失敗の型・
  評価軸・語彙

先行実装だけ調べると、既存物が無かったときに**素人設計で自作**してしまう。体系
知識だけ調べると、**車輪を上手に再発明**する。両方を1回で出すのがこのスキルの仕事。

## 既定は自作ではない

**自作は、既存が使えないことを立証して初めて選べる選択肢である。** これは趣味の
問題ではなく、記録の問題だ。自作を選ぶなら「何を見て、なぜ使えなかったか」が
残っていなければならない。残っていない自作は、調べなかった自作と区別がつかない。

判定は次の4つから選び、必ず根拠を添える:

| 判定 | 意味 | 求められる根拠 |
|---|---|---|
| **採用** | 既存物をそのまま使う | どれを・どのバージョンで・どう組み込むか |
| **改造** | 既存物を fork / 薄く包む | 元の何が足りず、改造が自作より安い理由 |
| **部分自作** | 既存物+自前の薄い層 | 境界線をどこに引いたか、なぜそこか |
| **自作** | ゼロから書く | **調べた既存物の一覧と、各々の却下理由** |

「自作」の根拠欄が「見つからなかった」だけなら、それは調査が浅い。検索語を変えて
もう一周する。世界にこれだけソフトウェアがあって本当に何も無い領域は、実際には
稀で、たいてい**呼び名を知らないだけ**である(下の「呼び名の壁」参照)。

## 手順

### 1. 調査対象を1文にする(最重要)

やろうとしていることを**実装非依存の1文**に還元する。ここを実装語彙で書くと、
その実装しか見つからない。

- 悪い: 「Playwright でサイトのフォントサイズを測るスクリプトを書く」
- 良い: 「実在の Web ページから構造的なデザイン特性(字階・余白・色)を機械的に
  抽出して比較可能な形にする」

良い方の1文なら、design token 抽出器、CSS 統計ツール、アクセシビリティ監査器、
web design census 系の学術研究——全部が候補として視界に入る。悪い方の1文では
Playwright のドキュメントしか出てこない。

### 2. 呼び名の壁を越える

**「無い」の大半は「その分野での呼び名を知らない」である。** 自分の語彙で1周
検索したら、見つかった資料が使っている**専門語**を拾い、それで2周目を回す。
ここを飛ばすと調査は必ず浅い。

- 自分の語彙: 「サイトの見た目を測る」
- 拾える専門語: design tokens / computed style extraction / visual regression /
  web design mining / stylometry
- 2周目はこの語で回す

領域名そのものが分からないときは、まず「この作業は何という分野の問題か」を単独で
問う。分野名が取れれば、その分野の教科書・survey 論文・定番ツールが芋づるで出る。

### 3. 並列ファンアウト(規模で切り替え)

調査は安価モデルの並列サブエージェントに委譲し、自分は**統合と裁定に徹する**
(fable-orchestrate の考えと揃える)。規模で手数を変える:

- **小さい判断**(ライブラリ1つ選ぶ、既知領域): インラインで WebSearch 数回。
  委譲の段取りのほうが高くつく
- **新規サブシステム・不案内な領域**: 4面で並列ファンアウト

4面の分担:

| 面 | 探すもの |
|---|---|
| **A. 既製品** | ライブラリ、CLI、SaaS、OSS。言語を跨いで探す(移植のほうが自作より安いことは多い) |
| **B. 体系知識** | その分野の定石、survey/教科書、標準・仕様、評価指標、失敗の型 |
| **C. 近傍事例** | 完全一致でなく「同じ問題を別の目的で解いた人」。ここが一番収穫が大きい |
| **D. 手元** | 自分のリポジトリ群・過去セッション・既存スキル。**社内の車輪が一番よく再発明される** |

D を落とさないこと。`~/working/` に同じものが既にある、は実際に起きる。

委譲するなら、プロンプトに下の「出典の規律」をそのまま課す。

### 出典の規律(委譲の有無に関わらず)

**一覧に載せる物には、1件ずつ出典を添える** — URL、または手元なら
リポジトリ相対パスとコミット。自分で調べても、サブエージェントに調べさせても、
この規律は変わらない。

出典の無い「〜があるらしい」は調査結果ではなく**思い出**である。思い出は採否の
根拠にできない。読み手(将来の自分を含む)が確かめられないからだ。名前を思い出
せるのに出典が出せないなら、それは「知っている」ではなく「聞いたことがある」で
あり、一覧に載せる前に確かめに行く。

手元(§3-D)で決着がついた場合も同じ。**「既にあるから外は見なくていい」は
成立しない** — 手元の物自体が既に車輪の再発明かもしれず、それを判定できるのは
外の一覧だけである。手元採用の場合こそ、外の候補を挙げて「それでも手元が勝つ
理由」を書く。

### 4. 見つけたものを実際に触る

採用候補の上位は、**動かしてから**判定する。README の機能一覧は当てにならない。
5分 動かして詰まったなら、それは「改造」か「自作」の根拠になる — 推測ではなく
観測として記録できる。

生きているかも見る: 最終コミット、未解決 issue の傾向、メンテナの応答。放棄された
プロジェクトの採用は、後で自作に戻ってくる。

### 5. 文書に残す

`docs/research/YYYY-MM-DD-<topic>.md` に1本残す(このリポジトリ群の既存慣習)。
**規範外・参考資料**として置き、正典や仕様を上書きしない。

文書が無いと、次のセッションが同じ検索を最初からやる。調査の値打ちの半分は
「二度と調べなくていい」ことにある。

```markdown
# <対象>の先行調査(YYYY-MM-DD)

*一次資料・規範外(参考文献)。仕様や正典の裁定を上書きしない。*

調査対象(実装非依存の1文): <§1 の1文>
使った検索語: <自分の語彙 → 拾った専門語>

## 判定

**<採用/改造/部分自作/自作>** — <根拠1-3行>

## 既存物の一覧

出典(URL / パス+コミット)は1件ずつ必須。手元の物も外の物も同じ表に載せる。

| 名前(出典) | 何をする物か | 生死 | 採否と理由 |
|---|---|---|---|

## この領域の定石(体系知識)

- <標準・評価軸・既知の失敗の型。それぞれ出典つき>

## 見送った候補と理由

- <名前>: <なぜ使えなかったか。「合わない」でなく、どの要件にどう足りないか>

## 自作する場合に引き継ぐもの

- <既存物から借りる設計判断・語彙・データ形式>
```

**「見送った候補と理由」を省略しない。** ここが次回の検索を短くする唯一の部分で
あり、また「本当に調べたのか」が読み取れる唯一の部分でもある。

### 6. 結論を持って戻る

報告は判定から始める。資料の羅列から始めない。人が欲しいのは「で、作るの?」の
答えであって、検索ログではない。

自作以外を選んだなら、その場で次の一手(どれをどう入れるか)まで出す。自作を選ぶ
なら、**既存物から借りる設計判断**を明示する — データ形式、語彙、失敗の型の回避。
ゼロから設計し直すのは、調査した意味を捨てる行為だ。

## 境界(他スキルとの関係)

- **superpowers:brainstorming** の**前**に走る。brainstorming は「何を作るか」を
  詰めるが、「そもそも作るか」は問わない。調査結果は brainstorming の入力になる
- **usecase-review** は需要側(欲しい人がいるか)、本スキルは供給側(既にあるか)。
  両方通って初めて新規実装が正当化される
- **process-research-rounds** は成果物が空虚と判定された**後**の、複数ラウンドの
  重い研究プログラム。本スキルは着手**前**の1発の軽い調査。深い知識欠陥が見えたら
  あちらに引き継ぐ
- **repo-history / global-session-map** は §3-D(手元の車輪)の実行手段として使う

## Red Flags(これを考え始めたら立ち止まる)

| 思考 | 現実 |
|---|---|
| 「要件が特殊だから既存では無理」 | 着手前に言えるのは仮説だけ。1つ動かしてから言う |
| 「探したけど無かった」(1周で) | 呼び名の壁を越えていない。専門語で2周目を回す |
| 「自作したほうが速い」 | 初版だけは、たいてい本当。保守・エッジケース込みで比べる |
| 「調べるより書いたほうが早い」 | 書き始めたら「作るか」は二度と問われない。順序が全て |
| 「ライブラリは重いから薄く自作」 | 薄い自作が薄いままだった例を、実際に1つ挙げられるか |
| 「社内には無いはず」 | 社内の車輪が一番よく再発明される。§3-D を飛ばさない |
| 「手元にあったから外は見なくていい」 | 手元の物が車輪の再発明かもしれない。外の一覧だけがそれを判定できる |
| 「名前は知ってるから出典は省く」 | 出典の出せない知識は思い出。確かめてから載せる |
| 「調査文書は後で書く」 | 書かれない。判定と同時に書く |
| 「この分野に定石なんて無い」 | 分野名を知らないだけのことが多い。分野名を単独で問う |
