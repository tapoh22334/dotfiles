## 2026-09-07 再実行時、既存リンクが `✗ link failed` と表示された

- **実物**: #184〜#188 を実登録した際、ボード登録と verify は全て成功したが
  `✗ link failed #185 → #184` 等が4行出た。GraphQL の生エラーを確認すると
  `Issue may not contain duplicate sub-issues` — **既にリンク済みのため拒否された**だけで、
  親子関係は無傷（`184 children: [185]` / `185 children: [186,187,188]` を確認）。
- **分類**: 内容欠陥（正常系を失敗として報告していた）。
- **5-why の終点**: `addSubIssue` の失敗を一律 `✗` として扱い、
  **冪等な再実行で必ず出る既存リンクを異常と区別していなかった**。
  マニフェスト方式は「再実行して安全」が前提なので、
  正常系が毎回 ✗ を出すのは設計と矛盾する。
- **なぜ直す必要があるか**: 無害な ✗ が常態化すると
  **本物の ✗ を読み飛ばす習慣がつく**。これは 08-04 の
  「失敗が出ていたのに成功として扱われた」と同じ構造の再生産であり、
  このスキルが潰そうとしている失敗そのもの。
- **修正**: エラー文字列を捕捉し、`duplicate sub-issues` の場合のみ
  `linked #c → #p (already)` として成功扱い。それ以外は
  **エラー本文を添えて** `✗` 表示（従来は本文が捨てられ原因が分からなかった）。
- **実験**: 修正後に同一マニフェストを再実行 → `✗` ゼロ、
  全リンクが `(already)` 表示、verify 全 `✓`。
- **回帰**: GitHub 側を直接照会し、ボード7件・`projectItems: 1` を確認
  （スクリプトの自己申告ではなく実物で検証）。

## 2026-09-07 プレースホルダ `-` がラベルとして作成されかけた

- **実物**: 前エントリの修正後、`--check` の出力に
  `· label: - (will be created)` が現れた。空欄埋めに使った `-` が
  ラベル一覧に混入しており、`apply` を実行していれば
  **リポジトリに `-` という名前のラベルが作成されていた**。
- **分類**: 内容欠陥（自分が入れた修正自体の不具合）。
- **5-why の終点**: 空欄対策として `-` を導入したが、
  **その `-` を読み出し側で戻す処理を label 抽出の2箇所に入れ忘れた**。
  `unblank` は `read` ループにしか適用しておらず、
  `cut -f5` による一括抽出経路が漏れていた。
- **修正**: label 抽出の2箇所に `grep -vx -- '-'` を追加。
- **実験**: `--check` を再実行し `· label: -` が消えることを確認。
  `type::epic` / `type::story` は従来どおり `✓`。
- **回帰**: 同マニフェストの `--verify` が引き続き
  ボード欠落5件を検出することを確認（前エントリの検出能力を壊していない）。
- **教訓**: プレースホルダ方式は「入れる側」と「戻す側」が対になる。
  片側だけの実装は、この種の混入を必ず起こす。

## 2026-09-07 Project登録が黙って落ち、1ヶ月気づかれなかった

- **実物**: `tapoh22334/ma-splitflap` #184〜#188（2026-08-04 13:51:50〜57 に作成）。
  Issue 5件は作成成功、`type::epic`/`type::story` ラベルも正しく付与、
  Epic→Story→Task の sub-issue リンクも成立。しかし全件 `projectItems: []` で
  **Projects ボードに1件も乗っていない**。ユーザーが 09-07 に
  「少し前に Projects に登録した記憶があるけど、どこかに行った？」と指摘して発覚。
  再現: `gh project item-add` は現在も
  `missing required scopes [read:project]` で失敗する。

- **分類**: 脱落欠陥（宣言した手順が黙って落ちた）。
  副次的に暗黙判断欠陥（前提条件の確認時期が定義されていない）。

- **5-why の終点**:
  1. なぜ登録されなかった → `project` スコープ不在で `item-add` が失敗
  2. なぜ報告されなかった → step 3 が step 1-2 と同一スクリプト末尾にあり、
     先行部分の成功で「概ね成功」と報告された
  3. なぜそれで通った → 完了判定が**成果物の実在確認になっていない**。
     旧120行目「途中で失敗したら止めて報告」は散文の注意書きで、確認する構造がない
  4. なぜ構造がない → 手順が「1→2→3 の順に実行せよ」という**命令列**で書かれ、
     各段の**検収条件**が定義されていない
  5. なぜ事前検出できなかった → 旧148行目のスコープ注意は
     「エラーが返ったらユーザーに伝えろ」という**事後対応**であり、
     **着手前の前提確認になっていない**
  → **根本原因: 前提の事前確認と各段の検収が構造として存在せず、順序だけが定義されていた。**

- **修正**（形を欠陥に合わせる: 脱落欠陥 → 構造スロット / 条件依存 → 観測可能な述語）:
  - `scripts/apply.sh` を新設。YAML マニフェスト（**意図した最終状態の宣言**）を
    入力に取り、(a) **preflight** で auth・スコープ・ボード到達性・ラベルを
    **最初の書き込み前に**検証し、失敗したら**一切書かずに終了**、
    (b) 作成後に **verify** で全ノードを GitHub から読み直してマニフェストと差分照合
    （issue 実在／ラベル／親子／ボード在籍）。
  - `references/manifest.md` にスキーマを新設。`issue:` で既存 Issue を
    採用でき、マニフェスト以前のツリーも retrofit 可能。
  - `scripts/miniyaml.py` を同梱（PyYAML 非導入環境でも追加インストール不要。
    チケットを切るのに pip を要求するのは摩擦が大きすぎる）。
  - SKILL.md step 3 を命令列から「マニフェスト→apply」に置換し、
    **実際の失敗事例を根拠として明記**。
  - **同時に引いた**: Mechanics 節のスコープ注意とサブ issue の node-ID 注意は
    スクリプトが吸収したため圧縮（+13行に対し冗長な散文を削除）。

- **実験**:
  - 再現テスト: `set -e` + `item-add >/dev/null` の旧パターンを再現し、
    シェル上はエラーが出るが**GitHub 上の状態は「Issue だけ存在」**になることを確認。
  - preflight: `--check` が `project` スコープ不在を検出し exit 1、
    `apply` が「Refusing to write: ... Nothing was created.」で停止することを確認。
  - **回帰検出テスト（本命）**: 実在の #184〜#188 を記述したマニフェストに
    `project:` を含めて `--verify` → **5件すべてを
    `✗ NOT on project board` として数秒で検出**。1ヶ月見逃された欠落を捕捉。
  - 対照: `project:` を外した同一マニフェストでは全件 `✓`（誤検知なし）。
  - バグ検出と修正: 実行中に bash が連続タブを畳んでフィールドがずれ、
    `issue` 番号が空読みされる不具合を発見（重複 Issue 作成の原因になりうる）。
    空欄を `-` で埋める方式に変更して解消。
  - `--verify` は preflight 失敗時も実行する例外を追加
    （壊れたツリーの診断こそ最も必要な場面のため）。

- **回帰**: 新規マニフェスト（`issue:` 無し・`project:` 無し）で `--plan` を実行し、
  自動ラベル付与と3階層の入れ子が従来どおり出ることを確認。
  既存の合格ケース（Issue とリンクの作成）は #184〜#188 の `--verify` が全 `✓` で成立。

- **未対応（記録のみ）**: `gh auth refresh -s project` はブラウザ対話フローのため
