# skill-map — 持っている道具を、用途から引けるようにする

スキルは増える。増えると「何を持っているか」を忘れ、**持っているのに使わない**状態になる。
この道具はそれを防ぐ。全件を並べるのではなく、**用途で束ねて一望させる**。

## この工程が疑う問い

> **この一覧を見た人は、次に使うスキルを選べるか?**

選べないなら、それは台帳であって地図ではない。台帳は網羅を誇るが、地図は
行き先を示す。89件を漏れなく並べた出力は前者で、役に立たない。

## まず台帳を集める

手で `find` を組まない。供給源が3系統あり、取りこぼす。

```bash
python3 ~/.claude/skills/skill-map/scripts/collect_skills.py --summary
```

| 引数 | 用途 |
|---|---|
| (なし) | JSON で全件。木を組む素材 |
| `--summary` | 人が読む要約。件数と未登録の確認に |
| `--group <名>` | その群だけ |
| `--source 自作` | 自作だけ(`plugin` / `公式配布` も可) |

**plugin の版に注意。** cache には旧版が残る(多いものは5版)。スクリプトは
`installed_plugins.json` が指す版だけを見る。cache 全体を走査すると同名スキルを
何重にも数えて、件数が数倍に膨らむ。

## 木の形

第1階層は**用途の群**。出所(自作/plugin)は属性として右に置く。
用途から引きたいのに供給源で分けると、「この仕事に使えるもの」が複数の枝に
散ってしまう。

```
スキル 89 件 — 自作 52 / plugin 36 / 公式配布 1

開発の規律 (10)                            1機能を作り切るまでの作法
├─ brainstorming            superpowers    作る前に意図・要求・設計を広げる
├─ writing-plans            superpowers    仕様から多段の実装計画を書き起こす
├─ test-driven-development  superpowers    実装の前にテストを書く
└─ … +7

パイプラインを回す (24)                    工程を定義された順に通す枠組み
├─ vf-pipeline              value-forge    工程の順序・ゲート・差し戻しを持つ
├─ vf-orient                value-forge    作らない選択肢を潰し価値仮説を固定
├─ speckit-specify          dotfiles       自然言語から仕様を起こす
└─ … +21 (vf- 10件, speckit- 14件)
```

記法は treeview に揃える(`├─ └─ │`、属性は右に列、省略は `… +N`)。
装飾記号や絵文字は使わない。

## 深さ

利用者の指定に従う。指定が無ければ**群 + 各群の代表3件**に畳み、
残りを `… +N` で示す。89件を全部出すと一望できない。

| 指定 | 出すもの |
|---|---|
| `L1` | 群の名前と件数だけ |
| `L2` | 群 + 各群の全スキル(名前と一行) |
| 指定なし | 群 + 代表3件 + `… +N` |
| 群名を指定 | その群だけを全件 |

**代表の選び方が効く。** 各群で「まずこれを覚えるべき」ものを前に出す。
`--group` を渡せば全件出るので、畳んだことを1行添えて道を示す。

**`… +N` の中身を展開しない。** 畳んだ先の名前を括弧に並べ始めると、
畳んだ意味が消えて木が元の長さに戻る。出すのは件数と、系列が分かる程度の
内訳まで。

```
良い: └─ … +21 (vf- 8件, speckit- 13件)
悪い: └─ … +21 (vf-requirements, vf-userflows, vf-harness, speckit-plan, …)
```

既定の深さでは**全体を40行程度**に収める。これは1画面で読める上限で、
超えると群の数を数えるだけの作業になる。

## 用途から引かれたとき

「こういう作業をしたいが、どれを使えばいいか」と聞かれたら、木を出す前に
**該当する群を特定して、そこだけ見せる**。全体の木は文脈として1行に圧縮する。

```
仕事を切る・追う (7件) — やることをチケットの形にして追う

  起票の前に        structuring-work   何をどの階層で切るかを決める
  GitHub へ載せる   github-tickets     Epic/Story/Task と Project
  腐りの点検        backlog-steward    削除候補を洗い出す
```

順序は群内の依存で並べる(前工程が先)。アルファベット順にしない —
**使う順に並んでいれば、それ自体が手順の説明になる。**

## 一行要約はどこから来るか

`references/groups.json` が持つ。description をそのまま使わない理由:
自作スキルの description は中央値172字、最長1349字あり、トリガー語の列挙を
含む。木に載せると原文より長くなる。

表に無いスキルは description の冒頭から機械的に圧縮し、`*` を付けて
「表未登録」と示す。**黙って落とさない** — 落とすと持っているのに
見えないスキルが生まれる。

## 分類表を育てる

新しいスキルを作ったら `references/groups.json` に1行足す。

```json
"群の名前": {
  "intent": "この群が何のためにあるか",
  "skills": { "skill-name": "60字程度の一行。体言止め" }
}
```

足さなくても接頭辞推定か「未分類」に出るので**木から消えることはない**。
ただし未分類が増えたら、それは群の切り方が実態に合っていない兆候。

**1群が20件を超えたら分割を検討する。** 一望できる単位は10件前後で、
それを超えると群の中でまた探すことになり、束ねた意味が薄れる。

## 隣の道具との境界

| 道具 | 対象 |
|---|---|
| **skill-map** | スキル台帳。対象が固定されている |
| treeview | 任意の対象を木にする汎用エンジン |
| session-map | 単一セッション内の subagent/fork |
| global-session-map | 全プロジェクト横断のセッション |

木の記法は treeview から借りるが、**対象がスキルに固定されている**点が違う。
「スキルを木にして」と言われたらこちら、「このチケット群を木にして」なら treeview。

## 出すもの・出さないもの

出すのは木と、木を読むための最小限。

- **出す**: 木、群の意図(1行)、件数、畳んだ旨
- **出さない**: 改善提案、「このスキルは使われていない」等の評価、
  スキルを整理すべきという助言

評価を混ぜない理由: 使っていないスキルがあっても、それが無駄かどうかは
持ち主にしか判断できない。地図が「この道は通るな」と言い始めたら、
地図として信用できなくなる。

整理の提案が要るなら、それは `skill-improver` か `backlog-steward` の仕事。
