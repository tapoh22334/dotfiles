# Adversarial Review — 主張の生存テスト

## 核心原理

**査読とは同意を集めることではない。主張を殺しにいって、殺せなかったものだけを通すことである。**
感想(「良い/気になる/検討の価値がある」)は査読ではない。査読の出力は**争点ごとの判定**
— その主張は真か偽か、そしてなぜそう決着したか — でなければならない。

**letter を守ることが spirit を守ることである。** 「全体としては良い」で個別の偽を通すのは、
査読の spirit の違反である。1つの偽を見逃した査読は、9つ褒めても失敗している。

## この形をとる(出力レシピ)

査読対象の各主張について、**必ず次の3つ組を出力する**:

```
■ 争点: <検証対象の主張を1文で。真偽が決着する命題に還元する>
  反証の試み: <この主張が偽だとしたら何が根拠になるか。全力で崩しにいく>
  判定: 【偽】/【真(反証に耐えた)】/【未決(決着に必要な情報)】+ 一行の理由
```

- **争点は命題に還元する。** 「decision_quality の軸が粗い」は感想。「tetris の
  decision_quality=賭け は偽であり、正しくは最適解探索」が争点。真偽が決まる形にする。
- **判定を必ず出す。** 反証を試みて崩れたら【偽】、耐えたら【真】、情報が足りなければ
  【未決】+「何があれば決着するか」。**留保のまま終えない** — 「怪しい」で止めるのは未判定であり査読未遂。
- **1件でも【偽】があれば、それを冒頭に置く。** 褒める前に、殺せた主張を先に出す。

## デフォルトを反転させる

普通のレビューは「正しいと仮定して粗を探す」。査読は逆で、**各主張を「偽だと仮定して
生存を試す」**。反証を試みて崩れなかった時にだけ【真】と書く。無罪推定ではなく、有罪推定から始める。

- 「この主張は正しいか?」ではなく「**これが間違っているとしたらどこか?**」を問う。
- 直感に反する主張(gomoku が independent、tetris が賭け)は最優先で崩しにいく。
  直感に反する = 偽である確率が高い、の信号。

## 独立性を確保する

**被査読物の生成過程を共有していると、枠の欠陥は見えない。** 同一起草系統の自己査読は
盲点を持つ(スキーマを自分で作った者は、そのスキーマが取りこぼす真偽を疑えない)。

- 可能なら、査読は生成に関与していない独立エージェント/独立コンテキストで行う。
- 自分が作った枠(分類軸・ラベル体系)そのものを疑う視点を明示的に持つ。
  「この主張はスキーマに従っている」は「この主張は真だ」を意味しない — **形式適合と真偽は別**。

## 足場に逃げない

書式・スキーマ・目的説明・命名規則の指摘は**査読ではなく別作業**(document-reviewer の領分)。
中身の主張が偽かもしれないのに「スキーマ定義を追加すべき」に紙幅を費やすのは、
**最も撃つべき的から逃げている**サイン。

- 「YAMLにすべき/目的が不明/出典がない」は真偽の判定を1件も生まない → 査読の成果ゼロ。
- 書式の問題に気づいたら1行で添えてよいが、**本体は必ず主張の真偽判定**に置く。

## Red Flags(この語を書き始めたら査読になっていない)

- 「〜かもしれない」「〜の可能性がある」「検討の価値がある」で段落が終わる → 判定を出せ
- 「全体としては整合的/模範的」→ 個別の偽を1件も殺していない証拠かもしれない。各争点に戻れ
- 「軸の解像度が粗い」「境界が曖昧」→ 個別命題への還元から逃げた一般論化
- 指摘の大半が書式・スキーマ・目的についてである → 足場に逃げている
- 反証を一度も試みずに「良い」と書いた → 有罪推定から始め直せ

## 規模を対象に合わせる

- 主張が数件: 全件に3つ組を出す。
- 主張が大量(数十〜数百): 直感に反する/影響が大きい/相互に矛盾する主張を優先抽出し、
  そこに反証を集中。**全件褒めるより、殺せる主張を数件確実に殺す方が価値が高い。**
- 独立検証者を複数立てられるなら、各主張に別々の反証者を当て、多数が崩せたら【偽】。

## natural-language-reviewer / document-reviewer との関係

あれらは**表現・構成・書式**の質を上げる(読みやすいか、AIっぽくないか、構造が整っているか)。
本スキルは**内容の真偽**を撃つ(その主張は事実か)。三者は補完的で、目的が違う。
「レビューして」と言われた時、求められているのが真偽なら本スキル、表現なら他2つ。混同しない。
