# 図を描く

図が読めなくなる原因のほとんどは、見た目の問題ではなく**意味論の破綻**にある。
同じ形が違う種類のものを指し、同じ矢印が違う関係を指し、隣り合うノードの
抽象度が揃っていない。これらは色を綺麗にしても直らない。

だから描く順序は、**意味を決めてから見た目を決める**。

## 描く前に決める4つ

図を1本の線も引く前に、この4つを決める。決まっていない図は必ず破綻する。

### 1. この図は何の問いに答えるか

図は文章の挿絵ではなく、特定の問いへの答え。問いが決まると、何を描かないかが決まる。

- 「データはどこを通るか」→ データフロー
- 「いつ何が起きるか」→ シーケンス
- 「今どの状態か」→ 状態遷移
- 「何がどう分類されるか」→ 階層

一つの図に二つの問いを詰めると、両方に中途半端な答えしか出せない。分ける。

### 2. ノードの種類を数える

図に登場するものを列挙し、**種類ごとに分ける**。典型的には:

- **もの**（データ、ファイル、成果物）
- **こと**（処理、変換、判断）
- **場所**（システム、サービス、コンテナ）
- **人**（役割、アクター）

種類が3つを超えたら、その図は欲張りすぎている可能性が高い。統合するか分割する。

### 3. 矢印の意味を定義する

矢印は「なんとなく次」ではない。図の中で矢印が意味することを一つに固定する。

- データが流れる
- 制御が移る
- 依存している
- 変換される

**一つの図で複数の意味を持たせない。** どうしても必要なら線種を変え、凡例で明示する。
向きも意味を持つ: 依存の矢印は「AがBを必要とする」向きに統一する（逆向きが混ざると
図全体が読めなくなる）。

### 4. 抽象度の階層を決める

同じ図の中で、「ffmpeg で 16kHz に変換」と「閲覧レイヤ」を並べてはいけない。
片方は実装の詳細、片方はシステム全体。**隣り合うノードは同じ縮尺で語る。**

判断基準: あるノードを説明するのに必要な前提知識の量が、隣のノードと同程度か。
大きく違えば粒度が揃っていない。詳細側を畳むか、別の図に分ける。

## 形が意味を持つ

読み手は形を手がかりに種類を判別する。だから**形と種類を1対1で対応させ、
図の中で一貫させる**。これが崩れると、読み手は毎回ラベルを読んで種類を
推測しなければならず、図である利点が消える。

Mermaid の場合:

| 種類 | 記法 | 見た目 |
|---|---|---|
| 処理・変換 | `A[処理名]` | 四角 |
| データ・成果物 | `A[(データ名)]` または `A[/データ名/]` | 円筒・平行四辺形 |
| 判断・分岐 | `A{条件}` | ひし形 |
| 開始・終了 | `A([始点])` | 角丸 |
| 外部システム | `A[[サービス名]]` | 二重枠 |

使う形は**3種類までに抑える**。それ以上は読み手が対応を覚えられない。
種類が多いなら、図を分けるサインだと考える。

## 色は最後、かつ無くても成立させる

**白黒で印刷して意味が失われる図は失格。** 色は既に他の手段（形、位置、
グルーピング、線種）で表現した区別を、補強するためだけに使う。

色に情報を載せてはいけない理由は実務的で、印刷、色覚特性、ダークモード、
スクリーンショットの劣化と、色が失われる経路がいくらでもあるから。

やってよい使い方:
- 既に形で区別済みのものを、さらに見つけやすくする
- 強調したい1箇所だけに使う（1色、1箇所）

避ける使い方:
- 色だけが種類の区別になっている
- 3色以上を意味の区別に使う
- 装飾のための色

## グルーピングで構造を見せる

囲みは、**個々のノードより上位の構造**を示すために使う。適切なグルーピングは
ノード間の線を減らし、図を劇的に読みやすくする。

囲む基準:
- 同じ場所にある（同一サーバ、同一サービス、同一プロセス）
- 同じ責務を持つ（同一レイヤ、同一チームの担当範囲）
- 同時に動く / 同時に落ちる

Mermaid では `subgraph`、SVG では矩形とラベル。

囲みが交差したり、3階層以上ネストしたら、それは構造が複雑すぎるか、
図が担いすぎている。分割を検討する。

## 並べ方が意味を作る

位置は無意識に読まれる。だから配置には一貫した規則を持たせる。

- **流れの方向を1つに固定する**。左→右か、上→下。混ぜない
- **並列なものは同じ列・同じ行に揃える**。揃っていないと、読み手は
  「なぜズレているのか」に意味を探してしまう
- **時間軸があるなら、必ず一方向に流す**。逆流する矢印はループか
  エラー経路に限り、それと分かる形にする
- **交差する線を減らす**。ノードの順序を入れ替えれば大抵消える。
  どうしても消えない交差が多いなら、その図の構造自体を疑う

Mermaid はレイアウトを自動決定するので、思い通りにならないことがある。
その場合はノードの宣言順を変える、`direction` を指定する、subgraph で
まとめる、といった手で誘導する。それでも破綻するなら SVG に切り替える。

## Mermaid と SVG の使い分け

**まず Mermaid を試す。** テキストで差分が取れ、Notion・GitHub・Markdown で
そのまま描画され、修正が容易。この利点は大きい。

SVG に切り替える判断:
- レイアウトを厳密に制御する必要がある（Mermaid の自動配置では表現できない）
- Mermaid に対応する図種がない
- 図が主成果物で、細部まで作り込む価値がある

SVG を手書きするときは、座標をベタ書きせず、グリッド（例: 20px 単位）に
スナップさせる。目視で「なんとなく揃える」と必ずズレる。

詳細は `references/mermaid.md`（記法と回避策）と `references/svg.md`
（手書きの型）を参照。

## 描いたら必ずレンダリングして見る

**ソースを読むだけでは図の欠陥は見つからない。** 交差、ラベルの衝突、ノードが
意図しない段に落ちる、囲みが伸びすぎる — これらは全て配置エンジンが決めることで、
テキストには現れない。構文が通ることと、図が読めることは別の問題。

Mermaid なら mermaid-cli で PNG にして目視する:

```bash
# サンドボックス無効化が要る環境が多い
echo '{"args":["--no-sandbox","--disable-setuid-sandbox"]}' > /tmp/pp.json
npx -y @mermaid-js/mermaid-cli@11 -i diagram.mmd -o diagram.png -w 1200 -p /tmp/pp.json
```

出力した PNG を実際に開いて見る。**そして直したら、また見る。** 一度で決まる
ことはまずない。レイアウトは局所的に直らず、ノードを1つ動かすと全体が組み替わる。

レンダリングできない環境なら、そのことを明示した上で構文の安全側に倒す
（ラベルは全てクォート、ノードIDは英数字、改行は `<br>`）。ただし
「構文は確認したが表示は未確認」と伝える。読み手が貼ってから崩れに気付くのは
最悪の体験になる。

### レンダリングで初めて見える典型的な欠陥

- **囲みをまたぐ線** — グルーピングの切り方が構造と合っていないサイン。
  素材の種類で切るか処理の段階で切るかを変えると解消することが多い
- **ラベルの重なり** — 自己ループや、同じノードから複数の矢印が出る箇所で起きる。
  中間ノードを足すと解決することがある
- **孤立して浮くノード** — ソース上は繋がっているつもりでも、配置上どこにも
  寄れずに空白へ飛ぶ
- **予想外の段落ち** — 出ていく辺が1本しかないノードは最下段へ落ちやすい

## 描いたら必ず自己点検する

レンダリングした図を見ながら、以下を確認する。ほとんどの図の欠陥はこれで見つかる。

1. **形の一貫性** — 同じ形が同じ種類を指しているか。データと処理が同じ形になっていないか
2. **矢印の一貫性** — 全部の矢印が同じ意味か。向きは揃っているか
3. **粒度の一貫性** — 隣り合うノードの抽象度が揃っているか
4. **白黒テスト** — 色を全部消しても意味が伝わるか
5. **交差** — 消せる交差が残っていないか
6. **孤立** — どこにも繋がっていないノードがないか。あるなら、それは図に必要か
7. **ラベル** — 名詞と動詞が混在していないか（処理は動詞、データは名詞で統一）

7が特に見落とされやすい。「音声結合」と「processed/*.wav」が同じ形で並んでいたら、
それは処理とデータの混同が起きている。

## よくある失敗

**全部を1枚に描こうとする。** 図の価値は捨てた情報の量で決まる。
描かなかったものが多いほど、残したものが際立つ。

**実装の詳細に引きずられる。** コードを読みながら描くと、コードの構造を
そのまま写してしまう。読み手が知りたいのは構造であって、関数の呼び出し順ではない。

**凡例で誤魔化す。** 凡例が長い図は、形と色の対応が複雑すぎるサイン。
凡例を読まないと分からない図より、凡例が要らない図のほうが良い。

**既存の図を直すとき、部分的に直す。** 粒度や矢印の意味が壊れている図は、
一部を直しても全体の一貫性は戻らない。描き直したほうが速いことが多い。
