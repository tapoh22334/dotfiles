## 図種の選択

問いに対応する図種を選ぶ。迷ったら `flowchart` で足りることが多い。

| 問い | 図種 |
|---|---|
| どこを通るか / 何がどう繋がるか | `flowchart` |
| いつ誰が何をするか | `sequenceDiagram` |
| どの状態にあるか | `stateDiagram-v2` |
| 何がどう分類されるか | `flowchart` の階層、または `mindmap` |
| 何がいつ起きるか（期間） | `gantt` |
| データの構造 | `erDiagram` / `classDiagram` |

`graph` は `flowchart` の旧記法。新規は `flowchart` を使う。

## 形と種類の対応

```
flowchart LR
    IN([入力]) --> P[処理]
    P --> D[(保存済みデータ)]
    P --> Q{判定}
    Q -->|該当| EXT[[外部サービス]]
    Q -->|非該当| OUT([終了])
```

| 記法 | 形 | 割り当てる種類 |
|---|---|---|
| `A[text]` | 四角 | 処理・変換 |
| `A[(text)]` | 円筒 | 永続データ・DB |
| `A[/text/]` | 平行四辺形 | 入出力データ・ファイル |
| `A{text}` | ひし形 | 判断・分岐 |
| `A([text])` | 角丸 | 始点・終点 |
| `A[[text]]` | 二重枠 | 外部システム |
| `A(((text)))` | 二重円 | 終端（状態図向き） |

3種類までに抑える。`[/text/]` と `[(text)]` を両方使うと、
読み手は「ファイルとDBの違いに意味があるのか」を考えることになる。
区別に意味がないなら片方に統一する。

## 矢印の使い分け

一つの図では**一つの意味**に統一するのが原則。複数必要なら線種で分け、
必ず凡例か文中で説明する。

```
A --> B      実線矢印   主たる関係（データが流れる / 制御が移る）
A -.-> B     点線矢印   副次的な関係（例外・条件付き・非同期）
A ==> B      太線矢印   強調したい経路（1本だけ）
A --- B      線のみ     関連はあるが方向がない
```

ラベルを付けると意味が明示できる:

```
A -->|該当時| B
A -.->|失敗時| C
```

**避けるべき使い方**: 点線を「なんとなく弱い関係」に使うこと。
点線が図の中で複数の意味を持つと、読み手は毎回文脈から推測することになる。

## グルーピング

```
flowchart TB
    subgraph pipeline["パイプライン（自動）"]
        A[取り込み] --> B[変換]
    end
    subgraph view["閲覧（手動）"]
        C[[ビューワ]]
    end
    B --> C
```

- ラベルは `subgraph id["表示名"]` の形にする。id だけだと日本語や
  記号でパースが壊れることがある
- ネストは2階層まで。3階層以上は図が担いすぎているサイン
- subgraph 間を跨ぐ矢印が多いなら、グルーピングの切り方が構造と
  合っていない可能性がある

## レイアウトを誘導する

Mermaid は自動配置なので直接制御できない。以下で誘導する。

**方向を指定する**

```
flowchart LR     左→右（横長。工程の流れ向き）
flowchart TB     上→下（縦長。階層・分岐向き）
```

subgraph 内で個別に指定もできる:

```
subgraph s1
    direction LR
    A --> B
end
```

**宣言順で並びを制御する**

Mermaid は宣言順を配置のヒントにする。並べたいノードは近い順序で宣言する。

**交差を消す**

線が交差したら、まずノードの宣言順を入れ替える。それで消えることが多い。
消えないなら、そのノードは別のグループに属している可能性がある。

**見えないノードで位置を調整する**（最終手段）

```
A --> B
A ~~~ C
```

`~~~` は非表示のリンクで、レイアウトにだけ影響する。多用すると
図の定義が読めなくなるので、本当に必要なときだけ。

## 色を使う場合

`classDef` で定義し、`class` で適用する。インラインの `style` は
重複が増えて保守しづらいので避ける。

```
flowchart LR
    A[自動処理] --> B[手作業]

    classDef auto stroke-width:2px
    classDef manual stroke-dasharray:4 3
    class A auto
    class B manual
```

**上の例では色を使わず、線幅と破線で区別している。** これが白黒でも
成立する書き方。色を足す場合も、この上に重ねるだけにする:

```
    classDef auto stroke-width:2px,fill:#e8f0ee
    classDef manual stroke-dasharray:4 3,fill:#f5ede4
```

色を消しても線幅と破線が残るので、意味は失われない。

## 環境ごとの制約

**Notion**
- ```` ```mermaid ```` のコードブロックでレンダリングされる
- ノードラベルに `(` `)` を含めるなら、ラベル全体をダブルクォートで囲む: `A["Notion (App)"]`
- 改行は `<br>`。`\n` は効かない
- `\(` `\)` のエスケープは使えない

**GitHub**
- Markdown 内の ```` ```mermaid ```` で描画される
- `classDef` の色指定はダークモードで見づらくなることがある。
  ここでも「色なしで成立する」原則が効く

**Claude Artifacts**
- ```` ```mermaid ```` フェンス、または HTML 内の `<pre class="mermaid">` で描画される

## 壊れやすい記法

**日本語ラベル** — 基本的に通るが、以下でパースエラーになる:
- ラベル内の `(` `)` `[` `]` `{` `}` → ダブルクォートで囲む
- ラベル内の `,` → ダブルクォートで囲む

```
A["音声（2トラック）"]     OK
A[音声（2トラック）]       環境によっては壊れる
```

**ノードIDに使える文字** — 英数字とアンダースコアに留めるのが安全。
日本語IDは環境によって壊れる。表示名はラベルで与える。

```
audio_in["音声入力"]      OK
音声入力["音声入力"]        避ける
```

**エッジラベルの `|`** — ラベル内に `|` を含めない。区切り文字と衝突する。

**セミコロン** — 行末のセミコロンは省略可。付けても害はないが、統一する。

## レンダリングして確認する

構文が通ることと図が読めることは別。必ず画像にして目視する。

```bash
# Chromium のサンドボックスで落ちる環境が多いので設定を渡す
echo '{"args":["--no-sandbox","--disable-setuid-sandbox"]}' > /tmp/pp.json
npx -y @mermaid-js/mermaid-cli@11 -i diagram.mmd -o diagram.png -w 1200 -p /tmp/pp.json
```

`-w` で幅を指定する。指定しないと極端に横長になり、実際の表示と印象が変わる。

**既定テーマは色が付く。** 「色を使っていない」つもりでも、Mermaid の既定
テーマ（`default`）はノードを薄紫で塗る。白黒で確認したいなら init で潰す:

```
%%{init: {"theme":"neutral", "themeVariables": {"primaryColor":"#ffffff","primaryBorderColor":"#333333","lineColor":"#333333","clusterBkg":"#ffffff","clusterBorder":"#999999"}}}%%
```

ただし **Notion では `%%{init}%%` が効かないことがある**ので、貼り付け用の
最終版からは外す。`classDef` で色を指定していなければ、テーマが変わっても
「色に意味を載せていない」という性質は保たれる。

### `direction` が効かないとき

全体が `flowchart LR` だと、subgraph 内の `direction TB` が無視されることがある。
subgraph を横に並べたいのか、中身を縦に流したいのかで全体の向きを決める。

実例: 3レーンを横に並べつつ各レーンを縦に流したい場合、全体を `TB` にして
subgraph を並列に置くほうが安定する（`LR` + 内部 `TB` より確実）。
