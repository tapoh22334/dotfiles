# Skill Improver — スキル欠陥の根本原因分析と対照実験による改善

## 核心原理

**スキルの欠陥は「文面を書き足したい気持ち」ではなく「観測された失敗の実物」から直す。**
失敗の実物なしの改訂は、次の儀式(読まれない文章)を増やすだけ。逆に、実物があれば
5-why で根本原因の層を特定でき、層が分かれば直し方の形(form)が決まり、形が決まれば
対照実験で効いたかを測れる。直感で当てた修正文は、たいてい既に守られなかった文と同じ
運命をたどる — **守られなかったスキルに文を足しても、足した文も守られない**。

## 対象 — 指示アーティファクト全般

直す対象はスキルだけではない。エージェントの行動を決める文面はすべて対象で、
同じ手順で扱う。種類ごとに「発火が住む場所」と「履歴を置く場所」だけが違う:

| 種類 | 発火が住む場所 | 履歴(improvement-log)の置き場 |
|---|---|---|
| SKILL.md | frontmatter の description | そのスキルのディレクトリ |
| CLAUDE.md(global `~/CLAUDE.md` / project) | 節見出し(見出しが場面を名指ししているか) | `~/.claude/improvement-log.md` |
| memory ファイル | frontmatter の description | `~/.claude/improvement-log.md` |
| settings.json / hooks | マッチャー・イベント名 | `~/.claude/improvement-log.md` |

優先順位は CLAUDE.md > スキル > 既定なので、**古い CLAUDE.md は新しいスキルに黙って
勝つ**。スキルを足しても CLAUDE.md を直さなければ、その行動は変わらない。

## 手順(1欠陥 = 実物→分類→5-why→形合わせ→実験→最小修正→記録)

### 1. 失敗の実物を確保する

改訂を書き始める前に、失敗の一次証拠を集めて書き出す:
- 何が起きたか(トランスクリプト抜粋・成果物・ユーザーの指摘の原文)
- スキルは何を意図していたか(該当節の引用)
- 期待と実際の差分1行

実物が無い(「なんとなく効いてない気がする」)なら、まず再現ケースを1つ作るのが先。

### 2. 欠陥を分類する(分類が直し方を決める)

| 分類 | 症状 | 直す場所 |
|---|---|---|
| **発火欠陥** | 該当場面でスキルが読まれなかった/無関係な場面で読まれた | frontmatter の description(本文ではない) |
| **理解欠陥** | 読まれたが意図と違う解釈をされた | 本文の曖昧箇所(用語定義・例の不足) |
| **遵守欠陥** | 理解した上で圧力下でスキップされた | 禁止+合理化テーブル+Red Flags(writing-skills の bulletproofing) |
| **脱落欠陥** | 作ると宣言した成果物・手順が黙って落ちた | 構造スロット(チェックリスト・必須欄) — 散文の注意書きでは直らない |
| **内容欠陥** | 従ったのに結果が悪かった(スキルの知識自体が誤り/不足) | 本文の知識を修正 — 根拠(新しい観測・研究)を引用して |
| **肥大欠陥** | スキルが長すぎて重要部が埋没/無駄な作業を誘発 | 削除。足すのではなく引く |
| **不在欠陥** | どの指示アーティファクトもその場面を扱っておらず、エージェントが既定の振る舞いで動いた | 新設。種類は観測で決める: 同じ場面が 2 回以上あり手順が複数段 → 新スキル(writing-skills で作る)/ 1〜2 文の方針 → CLAUDE.md の節 / 本人固有の事実 → memory。既存の近いスキルがあれば新設せず、そちらの発火か本文を広げる。ただし近いスキルが**機構**(登録・実行)で、欠けているのが**知識・判断規則**なら、新設して機構側から参照させる(構造化と登録の分離が例) |
| **矛盾欠陥** | 2 つの指示アーティファクトが食い違い、優先順位の高い(または古い)方が黙って勝った | 負けた側ではなく**古い側**を直し、方針の正本を 1 か所に決めて他方はそこを指す |
| **暗黙判断欠陥** | スキルが判断を要求するのに判断基準が書かれておらず、実行者の裁量で結果がぶれた | 観測可能な条件文(「Xが観測されたらA、なければB」)への置換 |

複数該当なら、上流(発火→理解→…)から直す。発火しないスキルの本文を磨いても無意味。

### 3. 5-why で根本原因の層を特定する

失敗が文面の外(実行中のプロセス・設定の読み込み・環境)にまたがるなら、因果の
歩きは five-whys-root-fix に任せ、その終点(根本原因 1 行)をここの入力にする。
逆に five-whys が「根本原因は指示の文面」に到達したら、修正はこの手順 4〜7 で行う
(分類・形合わせ・回帰・履歴が付く)。どちらか片方で済ませない。

失敗の実物に対して「なぜ」を繰り返す。各 why に**証拠**(トランスクリプトの箇所・文面の引用)を
付けること — 証拠のない why は推測であり、そこで連鎖を止めて再現実験に回す。
止めどころ: **スキルの文面・構造で直せる最深の層**まで(モデルの能力限界・ハーネスの仕様など
スキルの外にある原因に到達したら、それは記録して回避策を設計する — スキルに嘆きを書かない)。

よくある根本原因のパターン:
- description が本文の手順を要約している → エージェントが本文を読まず要約に従う
- 規則はあるが発火条件が主観的(「必要に応じて」「適切に」)→ 判断が実行者ごとにぶれる
- 宣言と追跡の分離(「3本作る」と書くが完了チェックの構造がない)→ 黙った脱落
- 例外条項(「〜の場合を除く」)が本則を飲み込む → 例外が常態化
- 2つのスキル/指示が矛盾し、エージェントが静かに片方を選ぶ(運用が変わったのに
  CLAUDE.md が古いまま、が典型。「未導入なら init」型の自動実行句があると確認なしに発火する)

### 4. 形を欠陥に合わせる(Match the Form to the Failure)

修正文の**形式**は分類で決まる(writing-skills の同名節と同じ原理):
- 遵守欠陥 → 禁止+合理化テーブル+Red Flags
- 出力の形の問題 → 「出力はこういう形」の正のレシピ(禁止の列挙は逆効果)
- 脱落欠陥 → テンプレートに必須スロット(散文の念押しは効かない)
- 条件依存の行動 → 観測可能な述語による条件文(無条件規則+免除条項にしない)
- ニュアンス条項(「ただし重要な場合は…」)は勝った文面も濁らせる — 例外は独立した条件文に

### 5. 対照実験で検証する(規模は欠陥に応じて)

- **発火欠陥**: 新旧 description で trigger 評価(should-trigger/should-not-trigger のクエリ集 —
  skill-creator の description 最適化ループが使えるならそれを使う)
- **文面の効き**: 新旧文面それぞれを新鮮なコンテキストのサブエージェントに与え、失敗を誘う
  タスクで **各5回以上**+**無誘導の対照群**。フラグの立った結果は必ず自分で読む(テンプレの
  復唱を効果と誤認しない)。**分散も指標** — 5回が5通りの解釈なら文面が縛れていない
- **構造スロット系**: 実験より検収 — 修正後のテンプレで1回実運用(または模擬実行)し、
  スロットが実際に埋まるかを確認
- **矛盾欠陥**: 直した後に、同じ主題(例: タスク管理・コミット規律)を他の指示アーティファクト
  全部で grep し、残った食い違いを列挙する。1 件も無いことが検収条件
- 対照群が失敗を示さないなら、直すものが無い — 改訂を書かずに終了する勇気を持つ

### 6. 最小修正+回帰

- 効いた候補だけを適用する。1欠陥1修正が原則(束ね改訂は原因と効果の対応を壊す)
- **同時に引く**: 修正で足した行数以上に、働いていない行を探して削る余地を検討
- 回帰: そのスキルの既存の合格ケース(過去に正しく機能した場面)が壊れていないかを、
  最低1ケースの再実行 or 机上照合で確認

### 7. 改善履歴を残す

**実験の成果物(クエリ集・対照実験の記録・机上判定表)は improvement-log.md の本文に
埋め込むか、対象スキルのディレクトリ配下に置く。** temp・スクラッチパッドに置いたものは
成果物ではない(セッションが変われば消え、由来も証明できない — 自己適用テストで実際に
散逸が起きた)。

対象がスキルならそのディレクトリ、CLAUDE.md・memory・settings なら `~/.claude/improvement-log.md`
に `improvement-log.md` を置き(無ければ作成)、1欠陥1エントリで追記:

```
## YYYY-MM-DD <欠陥の一言>
- 実物: <失敗の一次証拠の要約+所在>
- 分類: <7分類のどれ>
- 5-why の終点: <根本原因1行>
- 修正: <何をどの形で変えたか>
- 実験: <対照実験の設計と結果。省略したなら理由>
- 回帰: <確認したこと>
```

履歴は次の改善の入力になる(同じ欠陥の再発 = 前回の修正が効かなかった証拠として扱う)。

## Red Flags(これを考え始めたら立ち止まる)

- 「とりあえず注意書きを1行足そう」— 分類も5-whyもせずに書く文は読まれない文
- 「原因は明らかだから実験不要」— 明らかに見えた原因の半分は違う
- 「ついでにここも直そう」— 束ね改訂は対応関係を壊す。別エントリに分ける
- 「MUSTを大文字にすれば守られる」— 遵守欠陥の原因は強調不足ではない
- 「スキルを長くすれば網羅できる」— 肥大は独立した欠陥である
- 失敗の実物を引用せずに改訂を書き始めている — 手順1に戻る

## writing-skills との関係

新規スキルの作成・大改訂は superpowers:writing-skills(TDDサイクル)の領分。本スキルは
**運用中スキルのインシデント対応**であり、writing-skills の RED(失敗の観測)を「実運用で
既に起きた失敗」で代替し、GREEN/REFACTOR を上の手順4-6で行う小回りのループ。修正が
スキルの目的自体の再設計に及ぶと判明したら、writing-skills のフルサイクルへ昇格する。
不在欠陥で新スキルを作る場合も同じ: 分類・5-why・improvement-log の記録はここで済ませ、
起草は writing-skills に渡す(記録は `~/.claude/improvement-log.md` に置き、新スキルの
ディレクトリができたらそちらへ写す)。
