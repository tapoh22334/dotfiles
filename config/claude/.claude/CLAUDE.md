## 日本語の文章は観点ごとの基準に従う

日本語の文章を書く・修正するときは、書き始める前に `ja-review` スキルの観点表を確認して、
その文章に該当する観点の基準を読む。リポジトリの文書(README・設計書・技術書の原稿など)
には全観点が適用される。Issue・PR の本文とメモには言葉の観点が適用される。

文体・表記の規則は次のファイルにある。書くときから従えるように、ここで読み込む。

@~/.claude/doc-style.md

次の操作の前には、依頼がなくても `ja-review` を実行する。指摘を反映してから進める。実行してよいかの確認は求めない。

- Issue・PR を作る、または本文を書き換える(`gh issue create`・`gh pr create`・
  `gh issue edit`・`gh pr edit`、github-tickets の manifest を `apply.sh` に渡すとき)
- 日本語の文書を新しく書いた、または大幅に修正したあとでコミットする

会話の返答とコミットメッセージには適用しない。

## タスク管理は GitHub Issues + GitHub Projects

タスク・保留判断・アイデアは GitHub Issues で管理し、Project「All Work」
(owner tapoh22334, #4)に載せる。階層(Epic/Story/Task)と登録手順は
github-tickets スキルに従う。Backlog.md(`backlog/` ディレクトリ)は使わない。
新しいリポジトリでタスク管理の仕組みを初期化する前に、どの仕組みをなぜ使うかを
一言述べてから行う(自動で `init` しない)。

作業はチケットから始め、チケットで終える。着手前に対象 issue を確認し
(なければ作る)、完了時に close して「何を・なぜそう直したか」をコメントに
残す。コミットメッセージが語るのは差分の理由、チケットが語るのは判断の記録で、
後者は履歴を追わない人が読む場所なので省略しない。

## main への取り込みは PR 経由

`main` に直接コミット・push しない。作業は必ずブランチを切り、PR を作って
取り込む。ローカルで `git merge` して `main` を push する運用は取らない。

- PR 本文には「なぜ直すのか」を書く。差分の要約は GitHub が出すので不要。
- **CI の結果を見てからマージする。** 赤いまま通さない。
- 落ちているテストがあるときは、**変更前の baseline を測ってから**回帰か
  既存の失敗かを判定し、既存のものはその旨を明示する。混ぜて報告しない。
- 作業を頼まれたら、push・PR 作成・CI 確認・マージまでを含めて完了させる。
